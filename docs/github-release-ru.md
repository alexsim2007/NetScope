# Как выпустить NetScope на GitHub

В проекте подготовлены сборка двух платформ, черновик релиза, контрольные суммы и формы заявок. Workflow создаёт черновик; публикация выполняется вручную после проверки установщиков.

## Текущее состояние — 2 ноября 2026

Репозиторий [alexsim2007/NetScope](https://github.com/alexsim2007/NetScope) уже создан, исходники отправлены. Текущая версия — **0.1.2**, тег **v0.1.2** уже отправлен. Повторно создавать репозиторий, коммит и этот тег не нужно. Следите за [сборкой 0.1.2](https://github.com/alexsim2007/NetScope/actions/runs/41491686690), затем переходите к разделу 3. Старые неудачные запуски 0.1.0/0.1.1 остаются в истории.

В 0.1.1 исправлена установка зависимостей через `npm ci` на CI, в 0.1.2 — запуск Rust-тестов на Windows: тестовый EXE теперь содержит зависимость от Common Controls v6. Результаты проверок и оставшиеся ручные проверки записаны в [validation.md](validation.md).

Порядок первого выпуска: **отправить исходники → дождаться CI → записать версию → отправить тег → проверить черновик и установщики → опубликовать**. Сборки GitHub будут созданы заново из тега; они не наследуют локальный сертификат Mac.

Все команды ниже выполняются в терминале из каталога проекта:

```sh
cd /Users/al/Documents/ChatGPT/NetScope
```

Для сборки на GitHub локально устанавливать Windows или инструменты кросс-компиляции не нужно. Нужны аккаунт GitHub, Git и доступ к создаваемому репозиторию. Для локальных проверок нужны Node 24, npm и Rust не ниже версии из `src-tauri/Cargo.toml`.

## 1. Первый запуск: вход и отправка исходников

Для текущего репозитория этот шаг уже выполнен. При повторной настройке компьютера используйте GitHub CLI:

```sh
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh auth status
```

Код вида `ABCD-EFGH` появится **в терминале**, где запущен `gh auth login`. Введите его на открытой странице GitHub и подтвердите вход. Код не приходит по почте или SMS. Если он истёк, прервите команду через `Ctrl+C` и запустите вход заново. Пароль аккаунта GitHub не подходит для `git push` через HTTPS.

На GitHub создайте пустой репозиторий `NetScope` в своём аккаунте. Не добавляйте там README — он уже есть здесь. В терминале проекта выполните команды, подставив свой адрес репозитория:

```sh
git status --short
git add .
git diff --cached --stat
git diff --cached
# Проверьте состав: не должно быть баз, логов, .env, сертификатов, HAR/pcap и личных скриншотов.
git commit -m "NetScope: desktop network monitor"
git branch -M main
git remote add origin https://github.com/OWNER/NetScope.git
git push -u origin main
```

Замените `OWNER` на свой логин GitHub перед выполнением `git remote add`. Для HTTPS Git может предложить вход через браузер или менеджер учётных данных; пароль от аккаунта в команду не вставляйте. Если `origin` уже добавлен, проверьте его командой `git remote -v` и пропустите `git remote add` при правильном адресе.

Папки `artifacts`, `target`, `dist`, `.idea`, базы SQLite, логи, секреты и сертификаты исключены из Git. Данные вашей сети находятся в каталоге приложения ОС, не в исходниках. Каталог моделей содержит только модель и ревизию; поля подключения при выборе модели пустые.

Во вкладке **Actions** дождитесь проверки **Quality and desktop packages**. Windows собирается на Windows runner, macOS — на macOS runner. Скачанные артефакты CI — это ещё не публичный релиз.

## 2. Выбрать версию и создать тег

Текущий тег `v0.1.2` уже существует. Команды ниже — пример **следующего** выпуска 0.1.3, после внесения новых изменений. Внутренние манифесты требуют номер версии, хотя интерфейс не показывает бейдж версии:

```sh
node scripts/version.mjs 0.1.3
node scripts/version.mjs --check-tag v0.1.3
npm run check
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
git add package.json package-lock.json Cargo.lock src-tauri/Cargo.toml src-tauri/tauri.conf.json
git commit -m "Prepare release 0.1.3"
git tag v0.1.3
git push origin main
git push origin v0.1.3
```

Выполняйте команды по очереди; после ошибки остановитесь и исправьте её до создания тега. Скрипт меняет версии во всех манифестах и lock-файлах без обновления зависимостей. Тег должен совпадать с ними — workflow проверит это. Не переносите уже опубликованный тег на другой коммит.

## 3. Проверить черновик релиза

После отправки тега запустится **Подготовить черновик релиза**. Он соберёт обе платформы и создаст **draft prerelease** с файлами:

- `NetScope-Windows-x64-setup.exe`;
- `NetScope-macOS-arm64.dmg`;
- контрольные суммы `.sha256`.

Откройте [Releases](https://github.com/alexsim2007/NetScope/releases) под аккаунтом владельца и найдите черновик нужного тега. При ошибке исправьте её и создайте новый тег с новой версией. Для повторной сборки существующего тега можно использовать **Actions → Подготовить черновик релиза → Run workflow**, указав тег. Уже опубликованный релиз workflow не перезаписывает.

Черновик виден владельцу и участникам с нужными правами; обычный пользователь сможет скачать файлы со страницы Releases после публикации. Для ручного запуска workflow его файл должен уже находиться в основной ветке. Дополнительный личный токен не нужен: задача `draft` использует встроенный `GITHUB_TOKEN` с `contents: write`, задачи сборки имеют только чтение.

Перед публикацией:

1. Установите `.exe` на Windows 10/11 x64; проверьте запуск, WebView2, русский интерфейс, живое подключение, сворачивание в трей, возврат окна и выход.
2. Проверьте `.dmg` на другом Mac: установка, доступ к локальной сети, обе темы, значок, уведомления, меню и выход.
3. Проверьте [аппаратный чек-лист](hardware-test.md) и текущую [валидацию](validation.md).
4. Отредактируйте описание релиза: что поддерживается, что проверено и какие ограничения остаются.
5. Только после проверки нажмите **Publish release**.

Оставьте признак **pre-release**, пока расширенная проверка роутера и Windows не завершены. macOS-пакет рассчитан на Apple Silicon; Intel Mac в текущую матрицу сборки не входит.

Проверить контрольные суммы можно из каталога со скачанными установщиками и `.sha256`:

```sh
# macOS
shasum -a 256 -c NetScope-macOS-arm64.dmg.sha256
```

```powershell
# Windows PowerShell: ожидается True
$actualHash = (Get-FileHash .\NetScope-Windows-x64-setup.exe -Algorithm SHA256).Hash
$expectedHash = ((Get-Content .\NetScope-Windows-x64-setup.exe.sha256) -split '\s+')[0]
$actualHash -eq $expectedHash
```

## Если сборка или релиз не появились

| Ситуация                                                                        | Что сделать                                                                                                                                                                                          |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Тег отправлен, но workflow не запустился                                        | Проверьте `git ls-remote --tags origin`, наличие `.github/workflows/release.yml` в коммите тега и включённые Actions в Settings репозитория.                                                         |
| Ошибка проверки версии                                                          | Все манифесты и оба lock-файла должны соответствовать тегу. Запустите `node scripts/version.mjs --check-tag v0.1.2` для выбранного номера. После исправления исходников выпустите новый тег.         |
| `fatal: tag ... already exists`                                                  | Тег уже создан локально. Не создавайте его повторно; проверьте `git show --no-patch v0.1.2` и отправьте существующий тег через `git push origin v0.1.2`, если он ещё не отправлен.                |
| `Authentication failed`, пароль не принимается                                  | Выполните `gh auth login --hostname github.com --git-protocol https --web`, затем `gh auth setup-git` и повторите `git push`.                                                                       |
| Одна платформа собрана, другая упала                                            | Черновик создаётся только после успеха обеих платформ. Откройте упавшую задачу в Actions; временный сбой сервиса можно повторить через Re-run failed jobs, изменение исходников требует нового тега. |
| В задаче `draft` ошибка 403                                                     | Проверьте разрешение Actions на запись в репозиторий и ограничения организации. `contents: write` уже указан для этой задачи.                                                                        |
| Workflow отказывается менять опубликованный релиз                               | Это предусмотрено: создайте новую версию и новый тег.                                                                                                                                                |
| macOS сообщает об отсутствии доверенной подписи, Windows показывает SmartScreen | Сверьте заявленный статус подписи и контрольную сумму. Для публичного распространения настройте подпись по следующему разделу.                                                                       |

## 4. Подписи для публичного распространения

Локальная macOS-сборка на компьютере разработчика подписывается доступным Apple Development сертификатом. Это не Developer ID и не нотарификация. Сертификат не включён в репозиторий и не отправляется в GitHub.

Поставляемый workflow CI не содержит секретов подписи. Для macOS используется ad-hoc подпись (`APPLE_SIGNING_IDENTITY=-`); перед загрузкой артефакта CI проверяет `codesign --verify --deep --strict` и целостность DMG. Эта подпись не подтверждает разработчика и не заменяет Developer ID или нотарификацию; macOS может потребовать разрешить запуск в настройках конфиденциальности и безопасности.

Для публичного macOS-релиза настройте импорт Developer ID Application и нотарификацию по [руководству Tauri](https://v2.tauri.app/distribute/sign/macos/), заменив ad-hoc идентификатор в обоих workflow. Для Windows используйте отдельный сертификат/службу подписи по [руководству Tauri](https://v2.tauri.app/distribute/sign/windows/). Храните P12, пароли и ключи только в GitHub Secrets; не вставляйте их в YAML. Статус подписи нужно прямо обозначить в описании релиза.

Особенно важно для macOS: доступ к локальной сети зависит от идентичности подписи. Неподписанная/нестабильно подписанная сборка может не подключаться при включённом переключателе Local Network. После добавления подписи повторите живую проверку.

## 5. Принимать и разбирать обратную связь

В приложении раздел **Обратная связь** открывает [@allllllIlIl](https://t.me/allllllIlIl). Сообщения не отправляются автоматически. Пользователь сам выбирает, что написать. Есть шаблон и список данных для поддержки нового маршрутизатора.

В **Settings → General → Features** репозитория включите **Issues**. Формы для ошибки, идеи и нового маршрутизатора уже находятся в `.github/ISSUE_TEMPLATE`. Создайте метки `bug`, `enhancement`, `router-support`, `triaged`, `planned`, `in-progress`, `done`.

Рабочий процесс: Telegram → воспроизведение → обезличенная Issue → метка/приоритет → отдельная ветка → исправление/адаптер → проверки → черновик нового релиза. Личные переписки, пароли, cookie и исходные домашние дампы в Issues не копируйте. Для роутера используйте [шаблон заявки](router-support-ru.md).
